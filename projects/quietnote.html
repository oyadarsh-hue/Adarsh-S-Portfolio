Project film

What happens when two readers open one note?

A one-time link can be opened twice if concurrent requests check its availability before either marks it as consumed.

The approach

Authorize access with a conditional PostgreSQL update so only one concurrent request can claim a one-time note.

System view

How it works

CREATE AUTHORIZE CONSUME

  1. Create the share

    Next.js and Hono provide the interface and authenticated API; Prisma manages PostgreSQL records.

  2. Protect link access

    Random share tokens are stored as SHA-256 digests, with bcrypt-hashed optional access keys.

  3. Claim a note once

    A transactional conditional update handles expiry, consumption, revocation and view counts.

Features

  • Expiring and one-time share links
  • Optional access-key protection
  • Owner-controlled revocation
  • Database-backed concurrency controls

Outcome

A deployed proof of concept with documented database and browser verification. Notes are not end-to-end encrypted.

Engineering challenge

Making access rules hold under concurrent requests and avoiding accidental consumption by previews or page prefetching.

Implementation evidence

One-time access under concurrency

Claim a share with one conditional PostgreSQL UPDATE inside a transaction. Reading metadata does not consume the note.

Review scenario

Create a synthetic one-time note, open its link in two tabs and deliberately request access in both. One succeeds; later access is rejected. Test expiry, wrong keys and revocation separately.

A suggested walkthrough; linked tests are source evidence, not a new execution report.

Scope

This is an assessment proof of concept. Notes are not end-to-end encrypted; a successful server claim stays consumed if the response is lost.
