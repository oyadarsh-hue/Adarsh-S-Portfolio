Project film

Following a finding back to its source.

A security finding is difficult to review when the report loses its connection to the exact source code being analyzed.

The approach

Link multi-language security findings to source coordinates, defensive flow analysis and SHA-256 Merkle proofs.

Technology stack

Python
Review service and command-line tools
Static analysis
Language-aware inspection rules
SHA-256
Evidence fingerprints
Merkle trees
Grouped evidence verification

How it works

SOURCE FINDINGS PROOF

  1. Locate findings

    Language-specific rules inspect C/C++, Rust, Go, Python and C# while masking comments and string literals.

  2. Trace the data

    Boundary checks and defensive taint propagation support a review of untrusted data reaching risky operations.

  3. Review the evidence

    A Python standard-library service coordinates findings; optional Clang diagnostics and PDF exports support review.

Features

  • Multi-language source review
  • CWE and OWASP taxonomy mappings
  • Defensive taint-flow inspection
  • Merkle evidence and PDF audit output

Outcome

A documented local security-review platform with CLI and browser workflows. Findings support human review; they are not a guarantee that code is vulnerability-free.

Engineering challenge

Retaining exact source positions while filtering comments and binding report evidence to the reviewed input.

Implementation evidence

Reviewable source findings

Mask comments and strings while retaining offsets, then attach rule findings to source locations and SHA-256 evidence.

Review scenario

Compare the gets/strcpy samples with bounded alternatives. Inspect the matched location and review whether each finding is relevant.

A suggested walkthrough; linked tests are source evidence, not a new execution report.

Scope

Pattern-based rules and heuristic flow analysis support manual review. Evidence hashes establish integrity; they do not prove that a finding is correct or that code is secure.

Future work

Next engineering step
